HS Auto 代码级安全说明

1. 过去容易出问题的点
- 把授权、账号登录、游戏桥接混在同一条启动链路里，任一网络或授权异常都可能让“开脚本”卡住。
- UI 线程同步等待进程扫描、命名管道和动作确认，会表现为假死。
- Bridge 只要返回成功就继续，未校验插件名、PID、协议版本和状态后置条件，可能把错误响应当成合法局面。
- 本地设置/战绩直接覆盖写入，崩溃时容易留下半个 JSON。
- 安装器没有事务、备份、回滚和路径边界检查时，容易误删其他插件或写到错误目录。

2. 本初版采用的代码级防御
- 所有检测、管道请求、推荐读取和脚本循环都在后台任务运行；取消令牌贯穿启动、运行和退出。
- Bridge 握手必须同时满足 plugin=HsAuto.OpenBridge、当前 Hearthstone PID、protocol=1；不满足就停止。
- 命名管道限定为当前 Windows 用户 ACL，并拒绝远程客户端；请求/响应大小和超时有上限。
- 推荐先映射到当前实体和 OptionsPacket；动作提交后必须在 8 秒内观察到局面变化，否则停止，不自动重复提交。
- Bridge/解析失败带 reason 标签；编排层明确拒绝带 reason 的局面，不把 Unknown 当成大厅。
- 设置和战绩使用临时文件后原子替换；损坏 JSON 自动备份再恢复默认值；战绩去重，未知结果不写入。
- 安装先检查炉石已退出，写入前备份；每个目标限制在游戏根目录内，拒绝目录链接和越界 restore.json；失败自动回滚。
- 退出时先取消脚本，等待关键安装事务和普通后台任务，再保存设置并关闭窗口。
- 日志默认只写本机路径；不保存密码、Token、卡密、私钥或真实账号数据。

3. 进一步建议
- 生产版把 Bridge 请求结构改为明确的 DTO，不接受任意方法名；对每个命令做参数白名单。
- 为游戏版本、盒子版本、Bridge 协议维护兼容矩阵和回归夹具。
- 对发布包做 SHA-256 清单和签名；更新时验证签名后再替换。
- 对所有外部输入做长度、编码、枚举、PID、路径和时间窗校验。
- 只读模式应作为默认值；首次真实动作必须由用户明确切换并显示风险提示。
- 记录“读取失败/动作未确认/用户取消”三类不同原因，便于老师复现实验。

4. 论文中可以怎样表述
本项目不是通过修改炉石主程序或绕过授权实现功能，而是重建一个本地控制器：读取用户已正常启动的盒子推荐，经过状态校验后，通过受 ACL 保护的本机命名管道请求用户主动安装的 BepInEx Bridge；所有动作都采用提交后状态确认和失败即停策略。安全重点是减少 UI 阻塞、避免错误状态误操作、保证安装可回滚和不保存敏感凭据。
